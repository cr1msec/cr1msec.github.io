Understanding Shellshock

SecConceptsBashRCEPublished: Sep 2, 2026

A 2014 Bash bug that still roots boxes today, and why the underlying flaw is still worth understanding.

The short version

Shellshock (CVE-2014-6271 and a handful of related CVEs) is a vulnerability in Bash's handling of environment variables. If an attacker can control an environment variable that gets passed to a vulnerable Bash instance, they can smuggle arbitrary shell commands along with it. No memory corruption, no exotic exploitation chain, just Bash doing something it never should have done.

What Bash was actually doing wrong

Bash supports exporting functions through environment variables, a somewhat obscure feature where a variable's value looks like a function definition. When Bash starts, it scans its environment for variables formatted like this and imports them as callable functions. The bug was in how it parsed those definitions: Bash would parse the function body correctly, but then keep parsing past the end of it, executing whatever trailing text happened to be there as a normal shell command.

A malicious environment variable exploiting this looks like:

() { :; }; echo "this part runs as a real command"

The () { :; }; part is the "valid" function definition Bash expects. Everything after the semicolon is the payload, and Bash happily executes it.

Why CGI scripts were the perfect delivery method

This bug is only dangerous if something lets an attacker control an environment variable that reaches Bash. CGI is a textbook case: when a web server runs a CGI script, it converts HTTP request headers into environment variables so the script can read them. A header like User-Agent becomes an environment variable like HTTP_USER_AGENT, and if that CGI script is a Bash script (or invokes Bash internally), the attacker's header content gets parsed by the vulnerable code.

That means the entire attack can be delivered through a single crafted HTTP header:

curl
$ curl -H "User-Agent: () { :; }; echo; echo; /bin/bash -c 'id'" http://target/cgi-bin/vulnerable.sh

No authentication, no complex payload, just a header value shaped to look like a Bash function definition with a command tacked on the end.

Why this still shows up a decade later

The patched versions of Bash have been around since 2014, so in production this is genuinely rare now. It shows up constantly in labs and CTFs because it's a clean, self-contained teaching example: one specific parsing bug, one specific delivery mechanism, one clear "aha" moment when you understand why the payload is shaped the way it is. It's less about "this vulnerability is common in the wild" and more about "this is a perfect case study for how environment variable trust boundaries break."

The actual lesson

Any time user input crosses into an environment variable that gets interpreted by something else (a shell, an interpreter, a templating engine), that's a trust boundary worth being suspicious of. Shellshock is the canonical example, but the underlying pattern (attacker-controlled input landing somewhere it gets re-parsed as code) is the same shape as SSTI, command injection, and a dozen other bug classes. Recognizing the pattern matters more than memorizing the one CVE.
