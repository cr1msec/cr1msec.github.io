SQL Injection via WordPress Plugins

SecConceptsWordPressSQLi

WordPress core is usually solid. The plugins bolted onto it are a different story — and how BookingPress got popped is a good example of why.

Why plugins are the real attack surface

WordPress core has been through enough security scrutiny that finding a raw SQL injection in it directly is rare. Plugins are a different situation entirely — tens of thousands of them, written by developers with wildly varying security awareness, each one able to register its own database queries, AJAX endpoints, and admin-panel functionality. The security of a WordPress install is really the security of its weakest installed plugin, not the security of WordPress itself.

How the vulnerability surfaces

Version fingerprinting is usually the first real lead. WordPress plugins expose their version in predictable places — the plugin's readme file, HTML comments in rendered pages, or REST API responses — and once you have a plugin name and version, checking it against public vulnerability databases is often enough to find an existing, documented issue. That was the case here: a specific version of the BookingPress appointment plugin had a known SQL injection in one of its AJAX handlers.

The vulnerable endpoint accepted a parameter that got concatenated directly into a SQL query instead of being passed as a bound parameter — the same root cause behind essentially all SQL injection, just wearing a plugin-specific costume.

What made this one immediately useful

An existing Metasploit module already targeted this exact plugin and version:

msfconsole
$ use auxiliary/scanner/http/wp_bookingpress_category_services_sqli

Running it against the target dumped the WordPress user table directly — usernames and password hashes, extracted through the injection point without ever touching the login form. That's the practical payoff of SQL injection in a CMS context: it's rarely about a clever one-off query, it's about using the injection to read data the application was never supposed to expose.

Why the hashes weren't the end of it

One of the extracted hashes cracked to a usable password. But that password alone didn't unlock much — the real value came from the fact that people (and, just as often, applications) reuse credentials. Configuration files on the same server, found through separate enumeration, contained FTP and SMTP credentials that traced back to a completely different account. One SQL injection turned into a chain of credential reuse across multiple services, which is a far more common real-world outcome than SQLi leading directly to a shell.

The general lesson

For CMS-based targets, fingerprint every plugin, not just the core software — that's usually where the actual vulnerabilities live. And treat any credentials or hashes recovered through SQLi as a starting point rather than an endpoint: the next question is always "what else does this password unlock," because the answer is often "more than you'd expect."

Saw this played out fully — from plugin fingerprinting through cracked hashes to a credential-reuse chain that ended in root — in the MetaTwo writeup.
