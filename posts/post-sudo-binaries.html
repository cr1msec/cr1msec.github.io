When a Trusted Binary Turns Against You

SecConceptsSudoPrivEscPublished: Sep 2, 2026

Abusing sudo permissions on tools that were never designed to be run as root.

The trust assumption sudo relies on

Granting passwordless sudo on a specific binary feels like a controlled, minimal permission: "this user can only run this one program as root, nothing else." That framing quietly assumes the program itself has no way to break out of its intended purpose. For a lot of software, that assumption doesn't hold.

Any binary that can run other code is a liability

The danger isn't limited to obviously dangerous tools like bash or python. It extends to anything with a scripting layer, a plugin system, an exec-style function, or a way to shell out to the OS, even tools that look completely unrelated to system administration. Configuration management tools are a good example: many are built on top of a general-purpose language specifically so they can be extended, which means the "extension" mechanism is often just arbitrary code execution with extra steps.

If a tool like that is runnable via passwordless sudo, the actual permission being granted isn't "run this specific program." It's "run arbitrary code as root," just with one layer of indirection in between.

What this looks like in practice

The check that surfaces this is always the same:

sudo
$ sudo -l
User james may run the following commands on this host: (root) NOPASSWD: /usr/bin/knife

The output tells you what you can run. The actual research step is figuring out whether that thing can execute code. A quick check of a binary's documentation or a search for " exec" or " shell" is often enough to find a built-in escape hatch that the tool's authors added intentionally, for entirely legitimate reasons, that happens to also be a privilege escalation path when combined with unrestricted sudo access.

Why this keeps happening

The people configuring sudoers rules and the people writing the tool itself are almost never the same people making the same threat model. A tool's authors reasonably assume "if you can run this binary, you're already trusted." They didn't design it to be handed to a semi-trusted user via sudo. The sudoers rule, meanwhile, assumes the binary is "safe" simply because it's not an interpreter by name. Both assumptions are individually defensible and combine into a real gap.

The general lesson

Don't evaluate a sudo permission by what the binary is called. Evaluate it by what the binary is capable of. "It's not bash, so it's fine" is not a security analysis. If there's any code-execution surface reachable from that binary (a plugin system, an eval function, a scripting DSL, a shell-out feature), passwordless sudo on it is functionally equivalent to passwordless sudo on a shell.
