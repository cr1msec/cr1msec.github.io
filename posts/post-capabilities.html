Linux Capabilities Explained

SecConceptsLinuxPrivEscPublished: Sep 2, 2026

What cap_setuid does, and why getcap belongs early in enumeration.

The problem capabilities were built to solve

Traditionally, Linux permissions were binary: a process either ran as root, with access to everything, or it ran as a regular user with none of root's privileges. That's a bad fit for the real world. Plenty of programs need one specific root-level power (binding to a low port, changing their own UID, reading raw network packets) without needing full root access to the entire system.

Capabilities split "being root" into roughly 40 individual privileges that can be granted independently. A binary can be given exactly the power it needs, and nothing else, instead of the all-or-nothing root bit.

What cap_setuid actually grants

One of those capabilities, cap_setuid, lets a process change its own user ID, including changing it to UID 0 (root), without needing to already be root. In isolation, that sounds reasonable: some programs legitimately need to drop privileges after starting as root, and setuid is how they do it.

The problem is what happens when cap_setuid ends up on something that can execute arbitrary code. Python is the classic example. If the python3 binary itself has cap_setuid set:

getcap
$ getcap /usr/bin/python3.8
/usr/bin/python3.8 = cap_setuid,cap_net_bind_service+eip

...then any script run with that interpreter can call os.setuid(0) and immediately become root, because the interpreter itself carries the permission, not the script. This turns a fairly obscure kernel feature into a one-liner privilege escalation:

python3
$ python3 -c 'import os; os.setuid(0); os.system("/bin/sh")'

Why this is easy to miss

Capabilities don't show up in a normal ls -la permissions listing, and they're not what most people check first. SUID bits and sudo rules get far more attention. That's exactly why capabilities are worth checking specifically, rather than assuming a clean-looking file listing means there's nothing there. A binary can look completely ordinary in every conventional check and still be an instant root shell.

The check that actually finds it

A single command surfaces every capability set on the filesystem:

getcap
$ getcap -r / 2>/dev/null

It's cheap to run, rarely returns much noise, and when it does return something interesting, it's usually game over. It belongs early in any enumeration pass, before sudo and SUID checks.

The broader lesson

Capabilities are a genuinely good idea: least-privilege access instead of a binary root/not-root switch. The failure mode isn't the feature itself, it's granting a powerful capability to something that can be repurposed to run arbitrary code. The same logic applies well beyond Python: any interpreter, shell, or general-purpose binary carrying a capability like cap_setuid or cap_dac_override is worth treating as a potential root shell in disguise.
