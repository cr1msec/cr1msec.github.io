Docker Group Membership = Root

SecConceptsDockerPrivEsc

Being in the docker group is quietly treated as a minor convenience. It's actually root-equivalent — here's why.

What the docker group is for

By default, controlling Docker requires root, because the Docker daemon runs as root and talks to clients over a socket owned by root. The docker group exists purely as a convenience — add a user to it, and they can run docker commands without typing sudo every time. On the surface that sounds like a scoped, reasonable permission: "this user can manage containers."

Why that framing is wrong

Managing containers is managing the host. A member of the docker group can create a new container and freely choose how it's configured — including mounting any path from the host filesystem directly into that container:

docker
$ docker run --rm -it -u 0 --entrypoint sh -v /:/mnt some-existing-image

That single command starts a container running as UID 0 inside the container, with the entire host filesystem mounted at /mnt. From there:

chroot
$ chroot /mnt sh

...changes the root directory to the mounted host filesystem, effectively operating as root on the actual host, not just inside an isolated container. No exploit, no vulnerability being abused — every step here is Docker working exactly as documented. The docker group simply grants a capability equivalent to root, using entirely intended functionality.

Why it's easy to overlook

Docker access often doesn't announce itself. A fresh shell might initially fail to run docker commands at all:

permission denied while trying to connect to the Docker daemon socket

That error can read as "this user has no Docker access" and get dismissed. In practice it frequently just means group membership hasn't been picked up by the current shell session yet — a quick group refresh is enough to activate it:

newgrp
$ newgrp docker

The permission was there the whole time; the shell just hadn't caught up to the account's actual group membership yet.

Why this doesn't get flagged more often

Docker access gets mentally filed under "developer tooling" rather than "administrative privilege," so it doesn't get the same scrutiny that direct sudo rules or root SSH access would. The group name itself — docker, not admin or wheel — reinforces that framing. But functionally, there's no meaningful difference between "can run any container with any host mount" and "has root."

The general lesson

Any mechanism that lets a user control a privileged daemon — Docker, but also things like lxd, certain backup services, or anything else that runs as root and accepts unprivileged-user commands — deserves the same scrutiny as a direct sudo grant, even when the group name sounds harmless. "Convenience" permissions and "privileged" permissions aren't always different things wearing different names.
