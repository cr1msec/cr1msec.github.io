Methodology

Not a machine writeup — the actual process behind one. Structured after public CPTS-style methodology (credit at the bottom).

HOW I APPROACH A NEW BOX

Recon to root, in order

01
Full port scanNmap with service/version detection first. Non-standard ports are worth noting before enumeration even starts.
02
Web enumerationDirectory brute-force with ffuf/gobuster, check response headers, check for subdomains/vhosts. The real attack surface is often invisible from the main site alone.
03
Fingerprint everythingCMS version, server headers, software versions. Exact version numbers are what turn a vague hunch into a known CVE.
04
Check for known vulnerabilitiesMatch fingerprinted versions against public CVEs/exploits before trying anything custom.
05
Get a footholdExploit, land a shell, stabilize it. Grab the user flag to confirm real access before moving on.
06
Enumerate as the new usersudo -l first, always. Then SUID binaries, capabilities (getcap), cron jobs, config files, and any credential-management tools present.

$ whatweb http://TARGET
$ sudo -l
$ getcap -r / 2>/dev/null
$ find / -perm -4000 2>/dev/null
// the six lines I run on nearly every box
PRIVESC CHECKLIST

What I check first, and why

Roughly in this order, because they're cheap to check and catch the most common misconfigurations first.

  • sudo -l — passwordless sudo on a binary that can spawn a shell or run arbitrary code is one of the most common paths to root.
  • Linux capabilities (getcap -r / 2>/dev/null) — a binary with cap_setuid set is effectively a root shell in disguise.
  • Credential reuse — passwords or hashes found in one place (config files, database dumps, packet captures) almost always work somewhere else.
  • SUID binaries (find / -perm -4000) — always worth a pass, even when nothing obvious turns up immediately.
  • Direct RCE as root — sometimes there's no separate privesc step at all; the initial exploit lands as root outright.
